Cloud e Infraestrutura — Estudo de arquitetura

Microsoft Azure: decisões de arquitetura

O que a plataforma oferece para hospedar, proteger e observar aplicações, quando cada opção faz sentido e por que Azure e Azure DevOps não são a mesma coisa.

Escopo
Estudo conceitual. Nenhum serviço Azure aqui é apresentado como utilizado em projeto profissional.
Acesso
Sem assinaturas, recursos, nomes ou custos reais.

01Azure e Azure DevOps

Tabela
Microsoft AzureAzure DevOps
O que éPlataforma de nuvem com serviços de computação, rede, dados, identidade e observabilidade.Plataforma de colaboração de engenharia: repositórios, boards, pipelines e artefatos.
Onde a aplicação rodaÉ onde a aplicação pode ser hospedada.Não hospeda a aplicação. Entrega o código ao ambiente escolhido.
DependênciaPode ser usado sem Azure DevOps.Pode entregar para Azure, para servidores locais ou para outras nuvens.

Usar Azure DevOps para versionar e entregar um sistema não significa que o sistema esteja hospedado no Azure. São decisões independentes.

03Comparações que orientam a decisão

Tabela
EscolhaQuando favorece a primeiraQuando favorece a segunda
Máquina virtual × App ServiceSoftware que exige controle do sistema operacional, componentes instalados ou dependências legadas.Aplicações web padrão, em que a equipe quer reduzir operação e atualizar com rapidez.
SQL Server em VM × Azure SQL DatabaseRecursos do SQL Server que a versão gerenciada não cobre, ou controle total da instância.Menos manutenção: backup, alta disponibilidade e atualização ficam com a plataforma.
Load Balancer × Application GatewayDistribuição de tráfego na camada de transporte (TCP/UDP), sem interpretar HTTP.Roteamento por caminho ou host, terminação TLS e firewall de aplicação web, na camada HTTP.
Proxy reverso IIS × serviço de entrada do AzureServidor Windows único ou ambiente local, em que o IIS já é o ponto de entrada.Entrada gerenciada e escalável na nuvem, com proteção e roteamento oferecidos como serviço.
Windows Authentication × Microsoft Entra IDAplicação interna em domínio local, com Active Directory.Usuários e aplicações em nuvem; é possível combinar os dois em modelo híbrido.

Os pares não são equivalentes: cada um resolve um nível diferente do problema. A decisão correta depende de requisito, equipe e custo de operação.

04Arquitetura híbrida

Aplicações internas muitas vezes permanecem no ambiente local por dependência de banco, rede ou conformidade, e adotam serviços de nuvem aos poucos: identidade com Entra ID sincronizada ao Active Directory, monitoramento centralizado e armazenamento de arquivos. O ganho está em adotar cada serviço quando ele resolve um problema concreto, sem mover tudo de uma vez.
