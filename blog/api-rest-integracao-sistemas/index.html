API REST e integração entre sistemas: contrato, falha e repetição

O que separa uma integração que funciona na demonstração de uma que resiste ao uso real: contrato claro, autenticação, tentativas repetidas e idempotência.

Ligar dois sistemas costuma começar com uma chamada que funciona. O trabalho de verdade começa quando essa chamada falha pela metade, chega duplicada ou volta com um formato que ninguém combinou. Este texto reúne os padrões que tornam uma integração previsível. São princípios de engenharia, não a descrição de uma integração específica.

Comece pelo contrato

Antes de qualquer código, duas partes precisam concordar sobre o que trafega: campos, tipos, obrigatoriedade e códigos de erro. Um contrato tipado transforma divergência em erro imediato, em vez de dado silenciosamente errado.

Com FastAPI, esse modelo valida a entrada, gera a documentação e devolve erro 422 com a causa quando algo está fora do combinado.

O caminho de uma chamada

Cada etapa do desenho responde a uma pergunta: quem está chamando, o que ele enviou, o que acontece se o destino não responder e como saber depois o que ocorreu.

Autenticação e permissão

Tokens de curta duração, como os do OAuth 2.0, evitam que uma credencial vazada dure para sempre. O JWT carrega a identidade e as permissões já assinadas, o que permite ao servidor verificar sem consultar um banco a cada chamada. A regra prática é separar quem é (autenticação) de o que pode fazer (autorização) e negar por padrão.

Falhas transitórias e repetição

Redes falham por instantes. Repetir a chamada resolve, desde que se repita com critério:

  • esperar um tempo crescente entre as tentativas, para não sobrecarregar o destino;
  • limitar o número de tentativas;
  • repetir apenas erros transitórios (timeout, 503), nunca erros de validação (4xx).

Idempotência: repetir sem duplicar

Se a primeira chamada chegou, mas a resposta se perdeu, o cliente vai repetir. Sem cuidado, o efeito acontece duas vezes. A solução é uma chave de idempotência: o cliente envia um identificador único por operação e o servidor devolve o resultado original quando o reconhece.

Webhooks em vez de consultas repetidas

Quando um sistema precisa saber que algo mudou em outro, perguntar a cada minuto desperdiça chamadas e atrasa a notícia. Um webhook inverte o fluxo: o sistema de origem avisa. Em troca, o receptor precisa validar a assinatura da mensagem e aceitar o mesmo evento mais de uma vez.

Códigos de status, paginação e limites

Os códigos HTTP comunicam o resultado sem ambiguidade: 200 e 201 para sucesso, 400 e 422 para entrada inválida, 401 para falta de autenticação, 403 para falta de permissão, 404 para recurso inexistente, 409 para conflito e 429 quando o limite de uso foi excedido. O corpo do erro deve ter um formato estável, com um código legível por máquina e uma mensagem para pessoas.

Listas grandes precisam de paginação. A paginação por cursor, que usa o último item recebido como ponto de partida, é mais estável que a por deslocamento quando os dados mudam durante a leitura. Já o rate limiting protege o servidor de excesso de chamadas e deve informar ao cliente quando tentar de novo, com o cabeçalho Retry-After.

Rastreabilidade

Um identificador de correlação, repassado em todas as chamadas de uma operação, permite reconstruir o caminho entre sistemas quando algo dá errado. Sem ele, cada sistema enxerga só o seu pedaço.

Em resumo

Uma boa integração é a que se comporta de forma previsível quando as coisas dão errado: contrato validado, credenciais com prazo, repetição com limite e operações idempotentes. O resto é detalhe de ferramenta.
